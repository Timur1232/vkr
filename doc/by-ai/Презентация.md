## Слайд 2. О проекте

**Заголовок:** Что представляет собой проект

**Тезисы:**

- Это локальная система контроля версий и синхронизации файлов для обычных пользователей.
- Она даёт историю изменений, ветки и безопасное слияние.
- Устройства синхронизируются напрямую по локальной сети.
- Не нужны Git, командная строка, обязательный сервер и облачный аккаунт.
- Конфликты не останавливают слияние, а локализуются на уровне отдельного файла.

**Визуализация:** определение проекта крупным шрифтом в центре, вокруг — четыре иконки: история, ветки, синхронизация, конфликты. Или короткая схема «пользователь → устройства → общий репозиторий».

## Слайд 3. Проблема, сценарии и актуальность

**Заголовок:** Между сложностью Git и потерей контроля над версиями

**Проблема:**

- Несколько устройств: Linux, Android, эпизодический Windows; документы, PDF и папки проектов переносятся вручную.
- Git даёт историю, но требует staging, stash и rebase — несоразмерно повседневной задаче.
- Облако зависит от чужого сервера и создаёт конфликтующие копии: «финал», «финал_2», «финал_последний».

**Сценарии:**

- Учёба между ноутбуком и телефоном.
- Эксперимент в проекте с возвратом к исходному состоянию.
- Совместная работа двух-трёх человек по локальной сети.
- Восстановление случайно перезаписанного файла.

**Актуальность:**

- Похожие проблемы у студентов, малых команд и творческих специалистов.
- Anchorpoint: Git-клиенты неинтуитивны для не-программистов.
- Dropbox Community: конфликтующие копии появляются даже у одного редактора.
- Writing Stack Exchange и Hacker News: спрос на версионирование без Git.

**Вывод:** разрыв между потребностью в истории и сложностью инструментов.

**Визуализация:** три колонки — «Проблема», «Сценарии», «Актуальность» — с иконками; внизу строка источников мелким шрифтом.

## Слайд 4. Концепция

**Заголовок:** Распределённый репозиторий без обязательного сервера

**Тезисы:**

- Репозиторий — обычная папка с метаинформацией в корне.
- Каждое устройство хранит полную копию истории и работает офлайн.
- Синхронизация напрямую по локальной сети.
- Графический интерфейс; мобильный клиент — следующий этап.

**Визуализация:** три устройства (ноутбук, ПК, телефон) с одинаковым значком репозитория и двусторонними стрелками в локальной сети.

## Слайд 5. Функциональность: репозиторий и история

**Заголовок:** История без ручного управления файлами

**Тезисы:**

- Система сама отслеживает изменённые, добавленные и удалённые файлы.
- Сохранение состояния — одна операция, комментарий по желанию.
- Список состояний с содержимым каждого.
- Возврат к любому сохранённому состоянию.
- Метаинформация перемещается вместе с папкой репозитория.

**Визуализация:** мокап окна «История»: лента состояний с датами и кнопкой «Вернуться»; рядом — папка с метаинформацией.

## Слайд 6. Функциональность: ветки и слияние

**Заголовок:** Эксперименты без риска для основной версии

**Тезисы:**

- Ветка создаётся от любого выбранного состояния.
- Ветки изолированы: изменения в одной не затрагивают другую.
- Слияние — единственный способ интеграции.
- Rebase не реализуется: он переписывает историю и повышает риск ошибки.
- Ненужная ветка удаляется, не затрагивая остальные.

**Визуализация:** граф коммитов с двумя ветками, точкой расхождения и коммитом слияния; рядом — перечёркнутый rebase.

## Слайд 7. Функциональность: локализация конфликтов

**Заголовок:** Конфликт не останавливает слияние

**Тезисы:**

- Обычная VCS прерывает merge и требует решения здесь и сейчас.
- Для конфликтующего файла создаются ветки уровня файла.
- Файл переходит в состояние суперпозиции, остальные сливаются.
- Решение можно отложить: выбрать вариант, объединить фрагменты или оставить оба.
- Данные не теряются, процесс не блокируется.

**Визуализация:** две схемы рядом: слева — merge, остановленный на конфликте; справа — слияние продолжается, конфликт вынесен в отдельную ветку файла.

## Слайд 8. Функциональность: синхронизация и платформы

**Заголовок:** Обмен только необходимыми данными

**Тезисы:**

- Прямое соединение устройств по локальной сети, без сервера.
- Передаются только различающиеся данные.
- Список доверенных устройств.
- Полная работа офлайн; синхронизация — по необходимости.
- Приоритет Linux, затем Windows; Android — следующий этап.

**Визуализация:** схема «устройство — устройство» с указанием переданных блоков; рядом — три иконки платформ с пометками «MVP», «MVP», «перспектива».

## Слайд 9. Аналог: Gitless

**Заголовок:** Gitless: доказательство, что Git можно упростить

**Тезисы:**

- Исследование MIT: Perez De Rosso и Jackson, конференция Onward! 2013.
- Авторы разобрали около 2400 вопросов о Git на Stack Overflow.
- Сложность концептуальна: мешают не команды, а понятия staging, stash и «assumed unchanged».
- В Gitless они убраны, а ветка включает и рабочие, и зафиксированные версии файлов.
- Ограничения: CLI для разработчиков, нет синхронизации, мобильности и локализации конфликтов.

**Визуализация:** схема «Git → Gitless»: зачёркнутые staging area и stash; рядом — ветка как контейнер, включающий рабочие и зафиксированные версии.

## Слайд 10. Аналог: Git

**Заголовок:** Git: мощная механика, высокий порог входа

**Тезисы:**

- Распределённая VCS: полная история на каждом устройстве, ветки, слияние.
- Стандарт де-факто, огромная экосистема и инструменты.
- Сложная концептуальная модель: staging, stash, rebase, detached HEAD.
- Конфликт останавливает слияние и требует решения здесь и сейчас.
- Ориентирован на разработчиков: CLI, нет официального мобильного клиента, синхронизация файлов — отдельная задача.

**Визуализация:** две колонки «сильные стороны / ограничения»; в центре — граф коммитов; внизу — строка «ориентир по механике, но не по простоте».

## Слайд 11. Аналоги: системы контроля версий

**Заголовок:** VCS-аналоги требуют сервера или не дают веток

**Clustta:**

- Версионирование активов, крупные бинарные файлы, творческие команды.
- Минусы: сервер студии, нет веток уровня репозитория, нет мобильного клиента.

**Subversion:**

- Полноценная централизованная VCS: ветки, теги, отслеживание слияний.
- Минусы: обязательный сервер, слияние останавливается при конфликте.

**Вывод:** обе системы не дают распределённой модели и неблокирующего слияния одновременно.

**Визуализация:** две карточки с плюсами и минусами; внизу — общая строка «чего не хватает».

## Слайд 12. Аналоги: синхронизация и передача

**Заголовок:** Синхронизация есть, истории нет

**Syncthing:**

- Децентрализованная синхронизация без сервера, версионирование файлов.
- Минус: не VCS — нет коммитов, веток и слияния.

**FreeFileSync:**

- Синхронизация, резервное копирование, обнаружение конфликтов.
- Минус: не VCS, история — только архив копий.

**LocalSend:**

- Простая передача файлов по локальной сети.
- Минус: ни синхронизации состояния, ни истории.

**Вывод:** аналоги закрывают передачу данных, но не управляют версиями.

**Визуализация:** три карточки в ряд с иконками; под ними — шкала «передача → синхронизация → история», где каждая система закрывает только свою часть.

## Слайд 13. Сравнение и новизна

**Заголовок:** Новизна — в пересечении четырёх свойств

**Тезисы:**

- Свойства: распределённость, нелинейная история, локализация конфликтов, простота для нетехнического пользователя.
- Gitless даёт упрощение модели, но не синхронизацию и не локализацию конфликтов.
- Git, Clustta, Subversion, Syncthing и другие не соединяют все четыре.
- Собственный вклад: синхронизация, локализация конфликтов, графический интерфейс.
- Именно пересечение свойств, а не отдельный механизм, образует новизну.

**Визуализация:** матрица «свойства × системы» с отметками; строка «разрабатываемая система» заполнена полностью.
